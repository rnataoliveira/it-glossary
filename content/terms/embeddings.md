## Why does it exist?

Computers operate on numbers, not concepts. The words "dog" and "puppy" are completely different strings, yet they mean nearly the same thing. Traditional representations like one-hot encoding treat every word as equally distant from every other word, losing all semantic relationships. Embeddings solve this by mapping data into a continuous vector space where semantically similar items are placed close together and dissimilar items are far apart.

This representation unlocks capabilities that are impossible with raw text or categorical data: semantic search (finding documents by meaning, not keywords), clustering (grouping similar items automatically), analogy reasoning (king - man + woman = queen), and providing context to LLMs. Embeddings are the bridge between human-understandable content and machine-computable mathematics.

## Practical example of use

A product catalog uses embeddings to find items similar to a customer's query, even when the query does not share exact keywords with the product descriptions.

```python
from openai import OpenAI
import numpy as np

client = OpenAI()

def get_embedding(text: str) -> list[float]:
    """Generate an embedding for a piece of text."""
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text,
    )
    return response.data[0].embedding

def cosine_similarity(a: list[float], b: list[float]) -> float:
    """Compute cosine similarity between two vectors."""
    a, b = np.array(a), np.array(b)
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

# Embed product descriptions
products = [
    "Lightweight running shoes with breathable mesh upper",
    "Heavy-duty waterproof hiking boots for mountain trails",
    "Casual leather loafers for business casual wear",
    "High-performance basketball sneakers with ankle support",
]
product_embeddings = [get_embedding(p) for p in products]

# Search by meaning, not keywords
query = "comfortable shoes for jogging outdoors"
query_embedding = get_embedding(query)

# Rank products by similarity to the query
similarities = [cosine_similarity(query_embedding, pe) for pe in product_embeddings]
ranked = sorted(zip(products, similarities), key=lambda x: x[1], reverse=True)

for product, score in ranked:
    print(f"{score:.3f}  {product}")
# The running shoes rank highest even though "jogging" != "running"
```

## When to use

- When building semantic search that needs to understand meaning beyond keyword overlap
- When clustering or categorizing unstructured data (documents, support tickets, reviews) by topic or sentiment
- As input features for machine learning models where raw text or categorical data would be less informative
- When building RAG systems that need to retrieve relevant context from a knowledge base for an LLM

## When to avoid

- When exact keyword matching is sufficient and semantics are not needed (e.g., searching by product SKU or order number)
- When latency and cost constraints do not justify the overhead of calling an embedding API for every query
- When the data is purely numerical or structured and already has meaningful features that do not benefit from learned representations
- When privacy requirements prevent sending data to external embedding model providers

## Trade-offs

- **Semantic power vs. computational cost**: Generating embeddings requires running a neural network (locally or via API), which adds latency and cost compared to simpler text processing.
- **Dimensionality vs. precision**: Higher-dimensional embeddings capture more nuance but consume more storage and slow down similarity search. Lower-dimensional embeddings are faster but may lose fine-grained distinctions.
- **Model dependency vs. portability**: Embeddings are specific to the model that generated them. Switching embedding models requires re-embedding all existing data, which can be expensive for large datasets.

## Common small mistakes

- Comparing embeddings generated by different models, which use different vector spaces and produce meaningless similarity scores
- Not considering the context window limit of the embedding model — text that exceeds the limit is silently truncated, losing information
- Using embeddings for tasks where simpler approaches (TF-IDF, BM25) perform equally well, adding unnecessary complexity and cost
- Storing embeddings without the original text or metadata, making it impossible to inspect what a search result actually contains
- Assuming embeddings capture factual truth — they capture statistical co-occurrence patterns, which can reflect biases in the training data
